# budget-mbti-survey

> 작업 규칙은 **`AGENTS.md`** 에 있습니다. Claude 와 GPT 는 폴더를 열 때 그 파일을 자동으로 읽습니다.
> 기록은 이 `README.md` 한 곳에만 남기고, 지나간 것은 딱지를 붙이지 말고 지웁니다.


`budget-mbti`의 5·6부 성향 설문을 별도 사이트로 분리하기 위한 로컬
스캐폴드입니다. 현재 단계는 디자인이나 제품 규칙을 정하는 작업이 아니라,
원문 보존과 독립 빌드·D1 준비까지만 담당합니다.

## 지금 되는 것

- **설문이 실제로 돌아갑니다.** 첫 화면 → 15문항 → 유형 결과까지 이어집니다.
- **한 문항씩 넘깁니다.** 진행 바가 차오르고, 이전 질문으로 돌아갈 수 있습니다.
- **선택은 두 번에 나눠 받습니다.** 편을 먼저 고르고 세기(조금·많이·훨씬)를
  따로 고릅니다. 저장되는 점수는 그대로 1~6입니다.
- **결과는 캐릭터 카드입니다.** 유형 이름과 한 줄이 앞에 오고, 코드와 점수는
  접어 두었습니다. 정반대 유형과 한 축만 다른 유형도 함께 보여줍니다.
- 모두에게 **같은 15문항**을 냅니다(`app/survey-selection.ts`). 축마다 5문항씩,
  공통 9문항 + 서로 다른 6개 분야에서 뽑은 6문항입니다.
- **문항은 하나도 지우지 않았습니다.** 원본 99문항은 `survey-v3-data.ts`에
  그대로 있고, 분야를 먼저 고르게 하던 옛 방식(`getSurveyQuestions`)도
  살아 있습니다. 계획이 바뀌면 고정 목록만 갈아 끼우면 됩니다.
- 떼어 온 5·6부 JSX 원문은 `handoff/extracted-step5-step6.tsx.txt`에 그대로
  보존하고, 실행되는 화면은 `app/SurveyApp.tsx`에 새로 짰습니다.
- 원본 `globals.css`에서 설문·결과 화면에 쓰는 규칙만 떠 왔습니다(2,227줄).

### 인계 시점 상태

- 원본 저장소 기준: `e0ae3048b0d7e69cdd9b7960422a200d94faff52`
- `survey-v3-data.ts`의 99문항과 `scoring.ts`를 바이트 단위로 복사했습니다.
- `TYPE_MAP`, `AXES`, `TYPE_HIGHLIGHTS`를 원문 그대로 추출했습니다.
- `BudgetGame.tsx`에는 `SurveyQuestionCard`와 `step === 5`, `step === 6`
  JSX만 기계적으로 추출했습니다.
- D1에는 `responses`, `validation_responses` 두 테이블만 선언하고 새 초기
  마이그레이션을 생성했습니다.
- 기존 Cloudflare 프로젝트, 기존 D1, 기존 도메인에는 아무 작업도 하지
  않았습니다.

## 의도적으로 비워 둔 부분

- `.openai/hosting.json`에는 논리 D1 바인딩 `DB`만 있고 `project_id`가 없습니다.
- 도메인, Sites 프로젝트, 실제 D1 리소스, 배포는 생성하지 않았습니다.
- `/api/responses`는 아직 라우트로 마운트하지 않았습니다. 원문은
  `handoff/locked/api-responses-route.ts.txt`에 잠가 두었습니다.
- `/api/subscriptions`도 만들지 않았으므로 현재 404가 맞습니다.
- `getSurveyQuestions`의 선택 분야 종속 규칙은 그대로입니다.
- 5·6부 화면 문구는 수정하지 않았습니다.

떼어 온 5·6부 JSX 원문은 실행 대상 밖(`handoff/extracted-step5-step6.tsx.txt`)에
두었습니다. 타입 검사에서 파일 하나를 빼 두던 `tsconfig.json` 의 예외도 없앴으므로
**모든 소스가 검사를 받습니다.**

   합계 9만/1만/10만 원을 강제하므로 설문만으로는 저장할 수 없습니다. 응답을

   지금은 보여줄 수 있는 실제 숫자가 없어 자리를 비워 두었습니다.

5. 결과 화면 공유·결과 이미지 (원본의 이미지 저장 버튼은 예산 편성표를 찍던

## 게임판 기획 (진행 중)

설문을 **사람이 직접 움직이는 게임**으로 바꾸는 일입니다. 이 절이 기획서이자
GPT 에게 넘기는 주문서입니다. 따로 문서를 만들지 않습니다.

### 누가 무엇을 — 순서

1. **기획 — Claude + 사용자.** 이 절을 채웁니다. 항목마다 `[정함]` 이나
   `[정할 것]` 을 붙입니다.
2. **구현 — GPT.** **`[정함]` 만 만듭니다.** `[정할 것]` 에 걸리면 짐작해서 채우지
   말고 그 자리에서 멈추고 사용자에게 묻습니다. 짐작으로 만든 것은 기획을 다시
   열게 만들어 둘 다 일이 늘어납니다.
3. **재미 다듬기 — Claude.** GPT 가 만든 것을 받아 손맛(속도·연출·효과·소리)을
   더합니다. 그래서 GPT 는 아래 「다듬기 자리」 모양을 지켜서 짭니다.

단계가 끝날 때마다 — 아래 「게임판 — 지금 상태」 를 고치고, 폰 폭(360px) 화면을
한 장 이상 찍어 두고, 푸시합니다. 다음 사람은 그것만 보고 이어받습니다.

### 정한 것

- `[정함]` **일정 — 2026-10-28 후원주점에서 시제품 공개, 정식 출시는 2027년 초** (사용자, 2026-10-13).
  사용자: 「못하면 못하는 거지」 — 날짜에 맞추려고 기획을 줄이지 않습니다.
- `[정함]` **가장 중요한 것 — 관계, 그리고 다시 들어올 명분** (사용자, 2026-10-13).
  「마을이 포인트가 아니라 관계를 중시하고 들어올 명분이 있게 만드는 게 제일 중요」.
  기능을 고를 때 이 둘로 잽니다 — 이것이 누구와의(무엇과의) 관계를 만드나, 다시 올 이유가 되나.
- `[정함]` **가치지향 — 내 참여가 의미 있는 일이 된다** (사용자, 2026-10-13). 재미로 끝나는
  게임이 아니라, **내 선택이 모여 무언가가 되고 쓰인다는 명분**이 있어야 합니다. 이것이 보통 게임과
  다른 점입니다. 따라서 **응답을 모아야 합니다** — 10/28 재미판 때의 「저장 안 함」 결정은 게임판에는
  해당하지 않습니다(연락처는 여전히 안 받아도 됩니다). 모인 것이 무엇이 되고 어디에 쓰이는지는
  단체가 **실제로 할 수 있는 것만** 약속합니다.
- `[정함]` **친구 케미 같은 가벼운 궁합 장치는 쓰지 않는다** — 사용자: 「너무 짜치는 거 같아」.
- `[보류]` **시민행동 마을(오픈월드로 독상·상담소·지방재정을 잇기)** — 사용자가 고민하다
  「마을이 포인트가 아니다」로 정리. 이유: 사업을 모으는 입구는 이미 홈페이지·사업 지도가 하고,
  링크만 모인 마을은 더 불편한 홈페이지가 됩니다. 다시 열 기준 — 10/28 뒤 게임으로 들어온
  사람이 홈페이지보다 많은가, 건물마다 그 안에서 해 볼 거리가 있는가.
- `[정함]` **한 판에 하나만.** 시제품과 정식 출시의 첫 판은 **예산 성향(15문항) 하나**입니다.
  여러 가지를 한 판에 넣으면 무엇을 하는 게임인지 흐려집니다.
- `[정함]` **판(스테이지)을 덧붙일 수 있게 짠다.** 정식 출시 뒤 두 번째 판 후보는
  `local-finance` 저장소의 지방재정 자료(「우리 동네 예산」 같은 것). 두 사업은 따로 두고,
  게임이 그 자료를 판 재료로 **빌려 오는** 관계입니다. 지금은 구조만 열어 두고 만들지 않습니다.
- `[정함]` **사람이 직접 움직인다.** 버튼으로 고르는 설문이 아니라 캐릭터를
  조작하는 게임 (사용자, 2026-10-13).
- `[정함]` **게임판은 설문 v4 로 판정한다** — 축·문항·유형을 고쳤습니다(아래 「설문 v4」).
  채점 식은 v3 와 같습니다. 지금 사이트와 정적판은 v3 그대로 둡니다.
- `[정함]` **진보·보수 축을 만들지 않는다.** 시민단체가 그렇게 판정하면 편 가르기로
  읽힙니다. v3 의 「분배↔성장」 이 그 냄새가 나서 v4 에서 뺐습니다.
- `[정함]` **마스코트를 먼저 정하지 않는다** (사용자). 캐릭터는 기획 뒤쪽에서.
- `[정함]` **폰 세로·한 손으로 한다.** 후원주점처럼 서서·앉아서 폰 하나로 하는 자리가 기준.
- `[정함]` **지금 설문과 정적판은 그대로 둔다.** 게임은 따로 입구입니다.
- `[정함]` **2026-10-13 Claude 시제품(claude.ai 비공개 페이지)은 쓰지 않는다.**
  사용자가 기획부터 새로 하기로 했습니다. GPT 는 그것을 찾지 않아도 됩니다.
- `[정함]` **그림 재료는 CC0 를 먼저 쓴다.** 쓴 것은 아래 「에셋 출처」 에 한 줄씩
  적습니다(이름·주소·조건). 이미지 생성으로 뽑으면 프롬프트를 `game/prompts/` 에
  남깁니다 — 나중에 같은 화풍으로 더 뽑으려면 그 글이 있어야 합니다.

### 한 판의 흐름 `[정함]` (사용자, 2026-10-13)

```
들어오기 → 길 떠나기
  → 구간 1 (공통 3문항)
  → 구간 2 (분야 3문항: 교육·환경·문화)
  → 구간 3 (공통 3문항)
  → 구간 4 (분야 3문항: 보건·안전·국토)
  → 구간 5 (공통 3문항)
  → 도착 — 유형이 한 번에 드러남 → 공유
```

- 캐릭터를 직접 움직여 다섯 구간을 지납니다. 구간마다 질문 셋을 만나고, 고르면 다음으로 갑니다.
- **구간마다 장소가 있습니다** — 질문 내용과 맞는 곳(예: 구간 2 는 학교·공원·공연장이 있는 동네,
  구간 4 는 보건소·소방서·시골 마을). 「여기서 이걸 묻는구나」 가 자연스럽게 하려는 것.
  짝짓기는 아래 「정할 것」 2번.
- 중간에 기울기를 보여 주지 않습니다(아래 설문 v4 ③).

### 설문 v4 — 축·용어·루트 `[초안]`

사용자: 「축을 일단 수정해 봐. 루트도 제대로 설계하고. 문항 평가·논의는 사람들이 해야 해서
기다려야 하지만, 일단 네 판단으로 해 봐 — 특히 용어. 용어는 눈으로 보고 고칠게.」
(2026-10-13). 그래서 **전부 Claude 판단의 초안**이고, 사람이 검토하면 `확정` 으로 바꿉니다.

**내용은 `game/content.ts` 한 파일에 있습니다.** 축 이름, 문항 문구, 짧은 이름(표지판용),
루트, 유형 이름이 다 거기 있습니다. 문구를 고칠 때는 그 파일만 고치고
`npm test` 의 `tests/game-content.test.mjs` 가 통과하는지 봅니다(루트·축·짧은 이름 길이·판정을 확인).
채점은 `game/score.ts`.

**① 세 축 — 예산게임(budget-mbti)의 편성 축과 같은 이름·같은 방향으로 맞췄다**

| 어디에 (`hands`) | 시설·제도 | 사람에게 | 모두가 쓰는 바탕을 만드나 / 사람에게 바로 닿나 |
| 언제 (`time`) | 당장 | 두고두고 | 올해 효과 / 몇 년 뒤부터 오래 |
| 누구에게 (`reach`) | 좁고 깊게 | 넓고 고르게 | 꼭 필요한 곳에 몰아서 / 많은 사람에게 고르게 |

왜 —
- **v3 의 「분배↔성장」 을 뺐다.** 문항이 「세금을 줄여 국민이 쓸 돈을 늘린다」, 「가진 쪽에서
  걷어 나눈다」 처럼 지지 정당대로 답하게 생겼다. 예산게임도 8월에 같은 축을 「예산 범주에서
  읽히지 않는다」 며 버리고 「시설·제도↔사람에게」 로 바꿨다. 예산을 **어디에 쓰나**는 진영 없이 물을 수 있다.
- **「점진적 미래설계↔적극적 미래설계」 를 「당장↔두고두고」 로.** 양쪽 다 「미래설계」 라 무엇이
  갈리는지 안 보였다. 뜻은 그대로다.
- **「선별↔보편」 을 「좁고 깊게↔넓고 고르게」 로.** 뜻은 그대로고, 무상급식 논쟁 이후 정치 색이
  묻은 낱말을 피했다. 양쪽 다 좋은 말로 들리게.
- **예산게임과 같은 말을 쓴다.** 두 사업이 한 세계의 말을 쓰면, 편성해 본 사람과 설문에 답한 사람을
  같은 축 위에서 볼 수 있다. 방향(0/1)도 예산게임에 맞췄다 — 그래서 v3 와 유형 코드의 뜻이 다르다.

**② 문항 짓는 규칙 — v3 의 가장 큰 문제(축이 섞임)를 막는 규칙**

1. **한 문항은 한 축만 움직인다.** 두 선택지가 나머지 두 축에서는 같은 자리에 있어야 한다.
   `content.ts` 의 `holds` 칸에 묶어 둔 축을 적는다. v3 는 「지금」 쪽에만 「어려운 사람」 이
   붙어서, 분배를 중시하는 사람이 저절로 「지금」 을 골랐다.
2. **양쪽 다 좋은 말.** 한쪽에만 「어려운」 「공정」 「낭비」 같은 무게 실린 낱말을 두지 않는다.
3. **진영 신호 금지.** 세금 감면·증세, 특정 정부·정당의 정책 이름을 쓰지 않는다.
4. **같은 돈을 두고 고른다.** 규모가 다른 두 일을 견주지 않는다.
5. **짧게.** 선택지 한 줄, 짧은 이름(표지판·버튼) 8자 안쪽.
6. **무게(weight)는 검증 전까지 모두 1.** v3 의 구분력 3~5 는 짐작이었다. 응답이 쌓이면 재서 고친다.

**③ 루트 — 문항이 나오는 길**

- **문항은 모두 유형(세 축) 판정을 위해서만 있다** (사용자, 2026-10-13). 판정과 상관없는 문항을
  섞지 않는다 — 한때 Claude 가 「철마다 바뀌는 문항」 을 넣었다가 사용자가 걷어냈다. 그렇게 하면
  철마다 판정 재료가 바뀌어 뼈대가 무너진다. **다시 들어올 명분은 설문 밖에서** 만든다.
- **15문항 = 공통 9 + 분야 6** — v3 와 같은 뼈대. 공통 9문항은 분야 없이 가치만(축마다 3개).
  분야 6문항은 실제 예산 항목으로(축마다 2개, 서로 다른 여섯 분야, 국방·외교 뺌).
- **구간 다섯 × 3문항, 구간마다 세 축이 하나씩.** 1·3·5 구간은 공통, 2·4 구간은 분야 문항.
  같은 축 문항은 최소 세 칸 떨어진다(비슷한 질문이 붙지 않게). **모두가 같은 순서**로 답한다.
- **중간에 기울기를 보여 주지 않는다.** 구간을 지날 때는 진행만 보여 준다 — 앞 답을 보면 뒤 답이 끌려간다.
- `[보류]` 갈림 — 끝나고 어느 축이 가운데(±20 안)면 그 축 「결정 문항」 을 하나 더 내는 것.
  처음엔 안 한다. 응답이 쌓여 「반반」 이 많으면 그때.

**④ 여덟 유형 — 이름 초안**

코드는 어디에·언제·누구에게 순서, 1 이 오른쪽(사람에게·두고두고·넓고 고르게).
게임에서 캐릭터로 그릴 수 있게 **사람(역할) 이름**으로 지었다. 오른쪽 칸은 예산게임에서
같은 코드에 붙은 이름 — 하나로 맞출지는 사용자가 정한다.

| 코드 | 이름 | 한 줄 | 예산게임 이름 |
|---|---|---|---|
| 111 | 선생님 | 모두의 내일을 사람에게 심어요. | 함께 여는 내일 |
| 110 | 코치 | 꼭 키워야 할 사람을 골라 오래 곁에 있어요. | 다음 세대의 돌봄 |
| 101 | 밥 짓는 이웃 | 오늘, 모두에게 따뜻한 한 끼를 나눠요. | 일상의 받침대 |
| 100 | 구조대원 | 가장 급한 사람에게 지금 바로 달려가요. | 가장 가까운 돌봄 |
| 011 | 다리 놓는 사람 | 모두가 오래 건널 길을 놓아요. | 모두의 바탕 |
| 010 | 연구원 | 될 곳을 골라 먼 미래에 걸어요. | 미래를 겨눈 한 수 |
| 001 | 가로등지기 | 오늘 밤, 모든 골목에 불을 켜요. | 오늘을 굴리는 힘 |
| 000 | 수리공 | 가장 망가진 곳부터 오늘 고쳐요. | 급한 현장 먼저 |

**⑤ 채점** — v3 와 같은 식. 답 1~6 → 문항 점수 -2~+2 → 축마다 무게 가중 평균 × 50 → -100~+100.
점수가 0 보다 크면 1, 아니면 0(0 은 왼쪽 — 예산게임과 같은 규칙. v3 는 0 을 오른쪽으로 셌다).

**⑥ 사람이 검토할 것** — 문항 15개가 정말 한 축만 재는지(`holds`), 낱말이 한쪽으로 기울지 않는지,
유형 이름. 그리고 v3 의 공통 문항 중 살릴 것이 있는지(v4 는 축이 바뀌어 새로 썼다).

### 판정과 맞물리는 곳 — 구현 규칙

여기를 틀리면 게임은 돌아도 **유형이 틀리게** 나옵니다.

- **답 형식** — `Record<문항 id, 1~6>` (`game/score.ts` 의 `Answers`).
  1 이 `a` 쪽으로 가장 강하게, 6 이 `b` 쪽으로 가장 강하게, 3·4 는
  「조금」. 게임에서 무엇으로 고르든 끝에는 이 숫자 하나가 됩니다.
- **왼쪽·오른쪽** — `shouldSwapSurveyOptions(sessionId, questionId)` 가 참이면
  화면 왼쪽이 `b` 입니다. 게임 공간의 왼쪽 길·오른쪽 길 같은 배치도 **이것을
  따릅니다.** 왼쪽으로 가는 버릇이 결과를 쏠리게 하지 않으려고 둔 장치입니다.
  변환은 `app/SurveyApp.tsx` 의 `QuestionCard` 에 있는 것과 같습니다
  (`swapped ? 7 - 화면값 : 화면값`).
- **결과 계산** — `game/score.ts` 의 `scoreAnswers` → `typeCode`. 새로 계산하지 않습니다.
  문항·루트·유형은 `game/content.ts` 에서만 읽습니다.
- **응답 시간** — 문항이 **보인 순간**과 **답한 순간**을 지금처럼 기록해 둡니다
  (`SurveyTiming`, `buildResponseMeta`). 저장을 붙일 때 나중에 만들 수 없는 값입니다.
- **문항 99개는 지우지 않는다.** 원본 `survey-v3-data.ts` 를 고치지 않습니다.
- **게임 코드는 `game/` 폴더에** 둡니다. `app/`(v3 사이트)는 건드리지 않습니다.
  `app/survey-response.ts` 의 좌우 섞기·응답 시간 함수는 불러다 씁니다.

### 다듬기 자리 — GPT 가 이 모양으로 짜 두면 Claude 가 나중에 손댈 수 있다

- **조절 값은 한 파일에.** 걷기 속도, 카메라 거리, 연출 시간, 판정 거리 같은 숫자를
  `game/feel.ts` 하나에 모읍니다. 코드 곳곳에 숫자를 박으면 손맛을 고칠 때마다
  구현을 뜯어야 합니다.
- **진행은 신호로 낸다.** 「문항이 보였다」 「답을 골랐다」 「한 구간을 지났다」
  「도착했다」 같은 일이 생길 때 신호(이벤트)를 냅니다. 효과·소리·화면 흔들림은
  그 신호에 붙입니다. 진행 코드 안에 연출을 섞지 않습니다. 신호 이름은 구현할 때
  정해서 이 절에 적어 둡니다.
- **규칙과 그림을 나눈다.** 지금 몇 번째 문항인지, 무엇을 골랐는지는 그림 코드 없이
  시험할 수 있어야 합니다.
- 소리·효과는 **빈 자리만 있어도 됩니다.** 채우는 것은 3단계 일입니다.

- **`[정함]`·`[정할 것]` 딱지**를 붙인 이유 — 구현하는 쪽이 빈칸을 짐작으로 채우면
  기획을 다시 열어야 한다. 무엇이 확정인지 한눈에 보이게 했다.
- **「다듬기 자리」**(조절 값 한 파일, 진행 신호, 규칙·그림 분리)를 미리 적은 이유 —
  3단계에서 Claude 가 손맛을 더할 때 GPT 코드를 뜯지 않고 숫자와 신호에만 손대게 하려고.
- 판정과 맞물리는 규칙(답 1~6, 좌우 섞기, 응답 시간)을 따로 뺀 이유 — 게임은 멀쩡히
  돌아도 유형이 틀리게 나오는 실수가 가장 찾기 어렵다.
